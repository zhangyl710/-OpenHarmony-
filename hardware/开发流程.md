# 开发流程说明 —— 从写代码到上板

> 适用对象：**小熊派 BearPi-HM Nano（Hi3861）**，也就是阶段 0~3 用的那块板子。

---

## 0. 先看懂这张图，否则后面每一步都会别扭

小熊派这套工具链**不是单机开发**，而是两台机器分工：

```
┌─────────────────────────┐         ┌──────────────────────────┐
│  Ubuntu（编译机）        │  SSH    │  Windows（烧录 + 调试）   │
│                         │◄────────│                          │
│  · OpenHarmony 源码      │         │  · HiBurn（烧录）         │
│  · hb / scons / gn      │         │  · 串口终端（看日志）      │
│  · gcc_riscv32 交叉编译  │         │  · CH340 驱动             │
│                         │         │                          │
│  ▲                      │         │  ▲                       │
│  │ VSCode Remote-SSH    │         │  │ USB 线到开发板         │
│  └── 你在这里写代码      │         │  └── 烧录和看日志都在这   │
└─────────────────────────┘         └──────────────────────────┘
```

**为什么必须这样**：Hi3861 的交叉编译工具链（`gcc_riscv32`）、`hb`、`scons` 都是 Linux 工具；而海思的烧录工具 HiBurn 只有 Windows 版。

**VSCode 的角色**：装 `Remote - SSH` 扩展，直接连到 Ubuntu 上编辑源码。你感觉是在本地写代码，实际文件在 Ubuntu 上，终端也在 Ubuntu 上——编译完不用来回拷文件。

> 如果你不想装虚拟机：**WSL2 也可以**（见第 1.4 节），编译产物通过 `\\wsl$\` 路径在 Windows 里访问，HiBurn 照样能烧。

## 1. 环境搭建

### 1.1 编译机（Ubuntu）

**最省事的路子**：小熊派官方提供了**预装好全部工具链的 Ubuntu 镜像**（VMware 的 `.ovf` 文件），导入即用，默认密码 `bearpi`。先去小熊派官网/开源仓库找这个镜像，能省掉半天配环境的功夫。

**自己装的话**，Ubuntu 18.04 及以上 64 位，然后：

```bash
sudo apt-get install python3.8 python3-pip
sudo pip3 install setuptools kconfiglib pycryptodome six ecdsa
sudo apt-get install scons -y
```

另外需要 `gn`、`ninja` 和交叉编译器 `gcc_riscv32`（riscv32-unknown-elf-gcc），以及 `hb`（OpenHarmony 的构建入口）：

```bash
pip3 install ohos-build
```

> 工具链版本要和源码版本匹配。用官方镜像或按源码仓库的 README 走，别自己拼版本。

### 1.2 Windows 侧

| 装什么 | 干什么用 | 备注 |
|---|---|---|
| **CH341SER 驱动** | 认板子的串口 | 小熊派板载 CH340E；不装的话设备管理器里只有一个带感叹号的未知设备 |
| **HiBurn** | 烧录固件 | 海思官方工具，只有 Windows 版 |
| **串口终端** | 看程序日志 | MobaXterm / PuTTY / VSCode 的 Serial Monitor 扩展都行 |
| **VSCode + Remote - SSH** | 写代码 | 见下一节 |

### 1.3 VSCode 连接编译机

1. VSCode 安装扩展 **Remote - SSH**
2. `F1` → `Remote-SSH: Connect to Host` → 输入 `用户名@Ubuntu的IP`
3. 连上后 → `File → Open Folder` → 打开 OpenHarmony 源码根目录
4. 现在 `Ctrl+`` ` 打开的终端就是 Ubuntu 的终端

**如果 Ubuntu 在 VMware 里**：网络模式用「桥接」或「NAT」，在 Ubuntu 里执行 `ip addr` 查 IP。

> ⚠️ 用 VMware 时，**把虚拟机的 USB 捕获关掉**，否则 Windows 侧看不到开发板的串口——这是最常见的"板子插了但找不到 COM 口"的原因。

### 1.4 替代方案：WSL2

不想开虚拟机的话：

```powershell
wsl --install -d Ubuntu-22.04
```

然后在 WSL 里按 1.1 装工具链。编译产物在 `/home/<user>/openharmony/out/...`，Windows 里通过 `\\wsl$\Ubuntu-22.04\home\<user>\openharmony\out\...` 访问，HiBurn 直接选这个路径的文件即可。

USB 串口**不需要**转发到 WSL——串口是给 Windows 侧的 HiBurn 和串口终端用的。

## 2. 把代码放进源码树

阶段 1~3 的代码在 `hardware/firmware/bearpi_nano2_sensor/`，整目录拷进源码树：

```
<OpenHarmony 源码根>/
└── applications/sample/wifi-iot/app/
    ├── BUILD.gn                    ← 要改这一个文件
    └── sparkhub_node/              ← 新建，把我们的文件放进去
        ├── BUILD.gn
        ├── config.h                ← 记得改成你的 Wi-Fi 账号和主机 IP
        ├── sensor_node.c
        ├── sht40.c / sht40.h
        ├── relay.c / relay.h
        └── udp_link.c / udp_link.h
```

改 `applications/sample/wifi-iot/app/BUILD.gn`，在 `features` 里加一行：

```gn
lite_component("app") {
    features = [
        "hello:hello",
        "sparkhub_node:sensor_node",   # ← 加这行，去掉行尾逗号视你的 gn 版本而定
    ]
}
```

## 3. 编译（在 VSCode 的终端里）

**首次**要先选产品：

```bash
cd ~/openharmony
hb set
# 方向键选到：bearpi  →  bearpi_hm_nano
```

**之后每次改完代码编译**：

```bash
hb build -f     # -f = 全量重编，第一次和改了 BUILD.gn 之后必须带
hb build        # 只改了 .c 文件时可以用增量，快很多
```

产物是一个**打包好的单一固件**：

```
out/bearpi_hm_nano/bearpi_hm_nano/Hi3861_wifiiot_app_allinone.bin
```

> Hi3861 是轻量系统，整个系统 + 你的应用会打进同一个 bin，所以烧一次就全更新了。

**编译报错时先看这个**：如果提示找不到 `iot_i2c.h` / `wifi_device.h` 之类的头文件，是 `sparkhub_node/BUILD.gn` 里的 `include_dirs` 路径和你的源码树对不上。用这个命令定位实际路径，然后替换：

```bash
find ~/openharmony -name "iot_i2c.h"
```

## 4. 烧录（切回 Windows）

1. USB 线连板子，确认设备管理器里出现 COM 口
2. 打开 **HiBurn**
3. 点 **Refresh** → 在 **COM** 下拉框选你的串口
4. **Setting → Com settings** → **Baud 改成 921600**（这个波特率决定烧录速度，不是日志波特率）
5. 点 **Select file** → 选 `Hi3861_wifiiot_app_allinone.bin`
   - WSL 方案下路径形如 `\\wsl$\Ubuntu-22.04\home\<user>\openharmony\out\...`
   - 虚拟机方案下需要把 bin 从 Ubuntu 拷出来（共享文件夹 / scp）
6. 勾选 **Auto burn** → 点 **Connect**（按钮会变成 Disconnect）
7. **按一下板子的 RESET 键** → 开始烧录
8. 出现 **Execution Successful** 就成功了
9. **务必点 Disconnect 断开** —— 不断开的话，下次复位会自动重烧，而且串口被占着打不开

**按 RESET 的时机很关键**：必须在 HiBurn 点了 Connect 之后、15 秒内按。按早了或按晚了都进不了下载模式。

## 5. 串口验收（这就是阶段 1 的验收动作）

打开串口终端（MobaXterm → Session → Serial，或 VSCode 的串口扩展）：

| 设置 | 值 |
|---|---|
| Port | 和 HiBurn 同一个 COM |
| Baud | **115200** ← 注意！日志波特率和烧录波特率不一样 |
| Flow control | 关闭（None） |

打开后**按一下 RESET**，应该看到：

```
[node] SparkHub sensor node booting...
[node] SHT40 ok
[node] relay ok
[node] link init failed: -4 (will keep running locally)
[node] boot done
[sensor] NODE,N01,T=2543,H=5812,UP=0,TS=123456
[sensor] NODE,N01,T=2544,H=5809,UP=0,TS=133456
```

**阶段 1 的验收标准**：能稳定看到 `[sensor] NODE,...` 这行，而且**用手捂住 SHT40 传感器，T 值应该明显往上走**。走不动就是 I²C 没通。

`[sensor] SHT40 read failed` 反复出现 → 99% 是 E53 接口的 I²C 引脚号写错了，回去对原理图。

## 6. 日常迭代循环

配好之后，你每天就是在做这个循环：

```
① VSCode 里改 .c 代码
        ↓
② hb build -f         （VSCode 终端，约 1~3 分钟）
        ↓
③ 切到 Windows，HiBurn 重新选文件 → Connect → RESET
        ↓
④ 串口终端看日志，验证行为
        ↓
   回到 ①
```

**加速技巧**：
- 只改 `.c` 不改 `BUILD.gn` 时用 `hb build`（增量），快得多
- 用 Samba / VMware 共享文件夹把 Ubuntu 的 `out/` 目录映射到 Windows，烧录时就不用拷文件了
- 串口日志建议**同时在终端里重定向存文件**，这些日志后面答辩要用（见 `hardware/README.md` 第五节）

## 7. 改功能改哪里

### 先记住一件事

**烧录进板子的固件是"死"的。** 它不像网页刷新一下就变，也没有热更新。板子里没有你可以改的东西——**源头在 Ubuntu 上的源码里**，任何功能改动都必须走完整循环：

```
改代码（VSCode）→ hb build → 重新烧录 → 复位看日志
```

所以：改之前想清楚，一次改一处，改完烧一次。

### 想改什么，改哪个文件

| 我想改…… | 改哪个文件 | 具体位置 |
|---|---|---|
| Wi-Fi 账号密码 | `config.h` | `WIFI_SSID` / `WIFI_PSK` |
| 主机 IP / 端口 | `config.h` | `HOST_IP` / `HOST_PORT` |
| 节点编号（多节点演示） | `config.h` | `NODE_ID` |
| 上报频率 | `config.h` | `SAMPLE_INTERVAL_MS` |
| 灯亮的温度阈值 | `config.h` | `CONTROL_TEMP_HIGH` |
| 多久算主机失联 | `config.h` | `HOST_TIMEOUT_MS` |
| 新增一条控制指令 | `sensor_node.c` | `HandleCommand()` 里加一个 `strncmp` 分支 |
| 本地自治的策略 | `sensor_node.c` | `SensorTask()` 里 `if (!HostOnline())` 那一段 |
| 上报的数据字段 | `sensor_node.c` | `SensorTask()` 里的 `snprintf` |
| 换传感器型号 | `sht40.c` | 整个驱动重写，保持 `Sht40Read()` 接口不变 |
| 换通信方式（星闪） | `udp_link.c` | 整个文件替换，保持三个接口函数不变 |
| 加一路新传感器 | 新建 `xxx.c/.h` + 改 `sensor_node.c` + 改 `BUILD.gn` | 见下 |

**代码是刻意分三层的**：`config.h` 是调参面板、`sensor_node.c` 是业务逻辑、`sht40.c`/`udp_link.c` 是硬件接口。改一层不影响其他层——比如换星闪时，业务逻辑一行都不用动。

### 三种改动，编译要求不一样

| 改了什么 | 编译命令 | 原因 |
|---|---|---|
| 只改 `.c` 里的代码 | `hb build`（增量，快） | — |
| 改了 `config.h` 或任何 `.h` | **`hb build -f`**（全量） | 头文件改了，增量编译不保证重新编译依赖它的 `.c` |
| 改了 `BUILD.gn`，或加了新文件 | **`hb build -f`**（全量） | 构建图变了 |

**拿不准就一律 `hb build -f`**。慢一两分钟，但不会出现"明明改了却没生效"这种最浪费时间的情况。

### 加一路新传感器的完整步骤（以 BH1750 光照为例）

1. 新建 `bh1750.c` / `bh1750.h`，实现 `Bh1750Init()` 和 `Bh1750Read()`
2. **在 `BUILD.gn` 的 `sources` 里加上 `"bh1750.c"`** ← 最容易忘的一步
3. `sensor_node.c` 顶部 `#include "bh1750.h"`
4. `SensorNodeInit()` 里调用 `Bh1750Init()`
5. `SensorTask()` 的 `snprintf` 里加上字段，比如 `L=%d`
6. `hb build -f` → 烧录

**第 2 步忘了的典型症状**：编译时报 `undefined reference to 'Bh1750Init'` —— 文件在目录里但没参与构建。

### 如果你要改的是主机侧的决策逻辑

那不在这个工程里，在 `hardware/host/` 那边（Purple Pi OH）。节点只负责采集和听话，**"该不该开灯"这种判断放在主机**——这是刻意的，因为后面要把它换成昇腾上的推理，换的时候节点侧完全无感。

## 8. 常见坑速查

| 现象 | 原因 | 解决 |
|---|---|---|
| 设备管理器里没有 COM 口 | 没装 CH340 驱动 / VMware 捕获了 USB | 装驱动；关掉虚拟机 USB 捕获 |
| 串口终端提示 "Unable to open" | HiBurn 还连着没断开 | HiBurn 点 Disconnect |
| 串口全是乱码 | 波特率不对 | 日志用 **115200**，烧录用 **921600** |
| 一直烧不进去 | RESET 时机不对 / 波特率太高 | 点 Connect 后 15 秒内按 RESET；把 Baud 降到 460800 试试 |
| `hb: command not found` | `ohos-build` 没装或不在 PATH | `pip3 install ohos-build`，检查 `~/.local/bin` 在 PATH 里 |
| `ModuleNotFoundError: No module named 'jinja2'`（或其它模块） | hb 的 Python 依赖没装全 | `python3.8 -m pip install --user jinja2 pycryptodome setuptools kconfiglib six ecdsa requests`；**用 `python3.8` 而不是 `pip3`**，要和 hb 所在的 Python 版本一致（看报错路径里的 `python3.x`） |
| `pip` 报 `No usable temporary directory found` | `/tmp` 不存在、权限不对，或磁盘满了 | `ls -ld /tmp` + `df -h` 定位；常见修法 `sudo mkdir -p /tmp && sudo chmod 1777 /tmp`；临时绕过 `export TMPDIR="$HOME/tmp"`（**只在当前窗口有效**，编译时也会用到临时目录，建议根治） |
| 编译报找不到头文件 | `include_dirs` 路径不对 | `find ~/openharmony -name "xxx.h"` 定位后改 `BUILD.gn` |
| 每次复位都重新烧录 | HiBurn 没 Disconnect | 点 Disconnect |

## 8. 这个流程覆盖到哪一步

| 阶段 | 用哪块板子 | 流程和本文档 |
|---|---|---|
| 0~3 | 小熊派 Nano 2 | **就是本文档** |
| 2~3 的主机侧 | Purple Pi OH | 不同流程（OpenHarmony 标准系统 + DevEco Studio），另见 `host/` |
| 4 | 星闪节点 H3863 | 用小熊派 H3863 的 SDK（`fbb_ws63` 系列），流程类似但工具链不同 |
| 5 | 昇腾 Atlas | CANN + ATC + AscendCL，另一套工具链 |

**建议**：先把本文档的循环走顺，把 `[sensor] NODE,...` 这行日志稳定打出来，再碰后面的。**工具链没通就写业务代码，是所有嵌入式项目最大的时间黑洞。**
